# Execution Threat Model (MEGB-02)

This is the condensed threat-model reference for the isolated candidate
execution substrate. For operational detail (isolation controls, status
classification, cleanup, reproducibility), see
[`execution-sandbox.md`](execution-sandbox.md) — that document is
authoritative; this one exists as a focused pointer plus the formal
protected-assets/adversary framing CLAUDE.md's ADR process expects for
sandboxing/execution-safety decisions.

## Protected assets

- The host operating system and its filesystem, outside the container.
- This Git repository's working tree and history.
- Host environment variables and credentials (API keys, cloud credentials,
  SSH configuration).
- Canonical HumanEval/HumanEval+ solutions, hidden tests, and any future
  private adversarial tests (`src/dataset.py`'s privileged view).
- Evaluator source code and configuration.
- The availability of the evaluation process itself (one candidate must
  not be able to degrade or block evaluation of others).
- The integrity of the runner's own protocol response channel (a candidate
  must not be able to fabricate or corrupt its own result).

## Adversary model

Every `candidate_code` value passed into `CandidateExecutionRequest` is
treated as deliberately adversarial, generated by a system under
optimization pressure with every incentive to exploit weaknesses in the
measurement system (per CLAUDE.md's core hypothesis). The adversary is
assumed capable of:

- infinite loops and unbounded resource consumption (memory, processes,
  file descriptors, output volume);
- attempting to read or write outside its sandbox (host files,
  environment variables, other invocations' state);
- attempting outbound network access, including to common cloud metadata
  addresses;
- attempting to interfere with or forge the execution protocol itself
  (malformed output, direct file-descriptor manipulation, killing the
  interpreter).

The adversary is **not** assumed capable of a container-runtime or kernel
0-day that breaks Docker's namespace/cgroup isolation itself — see
"Out of scope" below.

## Trust boundary

```
Trusted controller (host)  <-- never executes candidate code -->  Untrusted worker (container)
```

The controller (`docker_backend.py`) only invokes the `docker` CLI and
parses JSON; it never calls `exec`/`eval` on candidate source. The
container has no bind mounts, no network namespace, no inherited
environment variables, a read-only root filesystem, dropped Linux
capabilities, and `no-new-privileges`. Full flag-by-flag detail is in
`execution-sandbox.md`'s "Isolation controls" table.

## Out of scope (explicitly, per MEGB-02's own non-goals)

- Formal verification of candidate correctness.
- Detection of algorithmic complexity classes (resource limits are a
  safety policy, not a complexity proof).
- Multi-tenant production-grade sandboxing or performance optimization of
  container startup.
- Defense against container-runtime or kernel zero-day vulnerabilities —
  this is Docker's standard isolation, correctly configured, not a custom
  hardened sandbox.
